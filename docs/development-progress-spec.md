# 开发进度同步规范

本规范用于保证每次任务完成后，项目进度、验收结果和下一步工作都有可追溯记录。它是项目级开发约束，Codex 在本项目中执行任务时必须遵循。

## 一、任务开始前

1. 读取 `docs/development-progress.md`，确认当前阶段、未完成事项和最近一次验证结果。
2. 判断本次任务属于哪个阶段；如果跨阶段，记录主要阶段和受影响阶段。
3. 对中型及以上任务，先明确目标、验收标准和预计修改范围。

## 二、任务完成判定

只有同时满足以下条件，任务才可以标记为“已完成”：

- 目标功能或文档变更已经落地。
- 相关验证命令已经执行；无法执行时必须记录原因。
- 已知错误、警告、限制和未完成项已经记录。
- `docs/development-progress.md` 已在同一任务中更新。
- 如果涉及 UI、产品方向或 Agent 适配，相关专项文档也已同步。

如果代码已经修改但验证未完成，记录为“已实现，待验证”；如果被外部条件阻塞，记录为“阻塞”，不得写成“已完成”。

## 三、每次任务完成后的强制更新

Codex 在最终回复前必须更新 `docs/development-progress.md`，至少包含：

```text
### YYYY-MM-DD · 任务名称
- 目标：本次任务要解决的问题
- 完成：已经实现或确认的内容
- 影响文件：关键文件路径
- 验证：执行的命令、测试数量和结果
- 已知问题：警告、限制或未完成项；没有则写“无”
- 下一步：下一项明确可执行的工作
```

更新必须追加到“变更日志”或对应阶段下方，不删除历史记录，不用模糊描述替代事实证据。

## 四、专项文档同步规则

根据任务类型同步以下文档：

| 任务类型 | 必须同步 |
|---|---|
| 阶段状态、验收、测试、阻塞 | `docs/development-progress.md` |
| 阶段目标、范围、排期变化 | `docs/mvp-development-plan.md` |
| UI、交互、布局、滚动条、组件规范 | `docs/design/ui-spec.md` |
| 产品定位、信息架构、交互原则 | `docs/design/context.md` |
| Agent 启动、历史解析、适配限制 | `docs/design/agent-adapter-probe.md` |
| 需求或验收标准变化 | `docs/mvp-prd.md` |

没有发生对应类型变化时，不要求机械修改所有文档；但必须更新主进度文档。

## 五、验证记录格式

验证记录应优先使用可复现命令，例如：

- `cargo fmt --manifest-path src-tauri/Cargo.toml -- --check`
- `cargo test --manifest-path src-tauri/Cargo.toml`
- `cargo check --manifest-path src-tauri/Cargo.toml`
- `pnpm check`
- `pnpm build`

记录测试数量、通过或失败状态，以及不影响通过的已知警告。手工验收要记录场景、结果和遗留问题，不能只写“已测试”。

## 六、最终回复要求

最终回复必须简要说明：

1. 本次完成了什么。
2. 进度文档是否已更新，并提供文件链接。
3. 验证是否通过。
4. 下一步或遗留问题是什么。

## 七、完成前自检

- [ ] 主进度文档已更新
- [ ] 阶段状态没有误标完成
- [ ] 验证命令和结果已记录
- [ ] 已知问题和下一步已记录
- [ ] 相关专项文档已同步或确认无需同步
- [ ] 最终回复包含进度文档链接
